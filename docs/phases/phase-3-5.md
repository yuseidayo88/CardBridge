## 1. 実装した内容

### 1.1 商品名解析（Phase 3）

| モジュール                | 役割                                                                              |
| ------------------------- | --------------------------------------------------------------------------------- |
| `parsing/normalizers.ts`  | 全角→半角、括弧統一、カード番号 / レアリティ / セットコード抽出、価格解析、類似度 |
| `parsing/psa-detector.ts` | PSA10 判定（多要素・確信度付き・三値判定）                                        |
| `parsing/title-parser.ts` | 決定的解析 + 店舗ルール + 構造化データの優先順位解決                              |

**推測しない設計を実装で担保しています。**

- **発売年とセット名は決して推論しません。** カード番号から年は分かりませんし、
  もっともらしい誤った年は eBay 検索の妥当性を下げたうえで、レビュアーの目には
  正しく見えてしまいます。`title_parser` は常に `unknown` を返し、
  構造化データかカタログ照合のみが埋めます
- **英語名も推論しません。** 日本語名の文字列操作からは生成せず、
  カタログ照合か翻訳（別プロセス、独自の provenance を記録）に委ねます
- 優先順位は `structured_data > supplier_rule > title_parser`。
  テストで「AI/汎用パーサが確定値を上書きしない」ことを固定しています

**PSA10 判定** は要件どおり「タイトルに PSA10 と書いてあるだけで信用しない」を実装。

- タイトル単独では **CONFIRMED になりません**（独立シグナル3つ以上が必要）
- 構造化データがタイトルと矛盾したら **即 REJECTED**
- 除外語: `PSA10相当`（＝未鑑定）、PSA9以下、他鑑定会社、BOX/パック/サプライ、
  まとめ売り、傷あり
- 他TCG（遊戯王・ワンピース・MTG・デュエマ・ヴァイス・シャドバ・DB）を別途フィルタ
- **曖昧なら REVIEW**。発火しなかったシグナルも含め全根拠を返却

### 1.2 同一商品統合（Phase 3）

`matching/match-key.ts` / `matching/scoring.ts`

要件の核心である**誤統合防止**を、非対称なコスト設計として実装しました。

> 見逃しはカタログが1つ余分になるだけで、管理画面で10秒で統合できます。
> 誤統合は**別のカードが1つの出品を共有し、買い手に違う物が届く**ことを意味します。

したがって:

- **カード番号の一致だけでは決して自動統合しません。** 番号はセット間で重複します
  （006/165 は複数セットに存在）
- **セットコードが両方判明していて異なる場合は REJECT**（拒否権であり減点ではない）
- グレード / 鑑定会社 / 言語の相違も拒否権
- 自動統合の最終条件: スコア ≥ 0.95 **かつ** カード番号とセットコードが両方一致
  **かつ** 全同一性フィールドが両側で判明していること
- **評価不能なシグナルは分母からも除外**。両店とも公開していない項目で
  減点されません
- 発売年の相違のみ **REVIEW**（メタデータ品質の問題であり別カードの証拠ではないため）

### 1.3 利益計算（Phase 5）

`profit/cost-model.ts` / `profit/min-price.ts`

**要件が挙げた全費目を名前付きフィールドとして実装。** 費目の省略は
利益を良く見せるのではなく、損する方向に数字を誤らせます。

仕入価格 / 国内送料 / 店舗手数料 / 国際送料 / 梱包費 / カテゴリー手数料 /
固定手数料 / 国際手数料 / 広告費 / 為替換算費 / 為替変動引当 / 返品引当 /
配送保険 / 署名オプション / 関税 / 輸入税 / 通関手数料 / 配送会社追加料金 / その他

**3シナリオ**（楽観 / 基準 / 悲観）。悲観シナリオは恣意的な悲観ではなく、
越境カード販売で実際に起きる3つをモデル化しています:
円が不利に動く（-5%）、送料が見積を超える（+15%）、返品が増える（引当×2）。

**関税は一律の前提を置きません。**

| モード                   | 扱い                                              |
| ------------------------ | ------------------------------------------------- |
| `BUYER_PAID`             | 当方コストではない                                |
| `MARKETPLACE_COLLECTED`  | eBay が決済時に徴収・納付。収益でもコストでもない |
| `SELLER_PAID`            | 当方コスト。de minimis 閾値を下回れば免除         |
| `CARRIER_QUOTE_REQUIRED` | **金額を作りません**。警告を出し手動確認へ        |
| `MANUAL_REVIEW`          | 同上                                              |

**最低販売価格の逆算**は二分法で実装しました。閉形式は導出可能ですが脆く、
費目を1つ足すたびに再導出が必要で、忘れれば静かに誤ります。
`calculateProfit` そのものを使って解くので、**判定と逆算が食い違うことがありません**。

既定は**悲観シナリオ**で解きます。

### 1.4 仕入れ先選択（Phase 5）

`pricing/sourcing-selector.ts`

「最安の商品価格」ではなく**実質仕入原価**で比較します。

```
実質原価 = 商品価格 + 国内送料 + 店舗手数料
         + 取り寄せ日数 × 日額
         + (1 - 信頼度) × 原価 × リスク係数
```

キャンセルリスクを**原価に比例**させているのが要点です。
信頼度95%の店でも、¥100,000 のカードと ¥3,000 のカードでは
期待損失がまったく違います。

**在庫数の扱い**（要件の明示事項）:

- 店舗が個数を公開しない → **常に 1**。「在庫あり」から数を推測しません
- 個数を公開 → `max(0, 在庫数 - 安全在庫)`
- **複数店舗の在庫を合算しません。** 2店が1枚ずつ持っていても2枚売れる保証はなく、
  2件目は未検証の仕入れが必要になります
- eBay 数量上限は既定 1

### 1.5 eBay 出品準備

`listing/sku.ts` / `listing/title-builder.ts` / `listing/eligibility.ts` /
`ebay/inventory/condition-descriptors.ts`

**SKU** は重複出品を防ぐ主キーです（DB のユニーク制約が効く単位）。
決定的・衝突耐性・安定（価格や在庫が変わっても不変）・可読の4条件を満たすため、
可読部分（切り詰めで情報が落ちる）＋ 完全な同一性のハッシュ、という構成にしました。

**英語タイトル**は AI に自由作文させず、構造化フィールドから決定的に組み立てます。
AI の寄与は**英語カード名1項目のみ**です。

- 80文字上限を必ず遵守（超過は ErrorCode 70）
- 予算超過時は検索価値の低い順に脱落: セット名 → レアリティ → GEM MINT → 年 → 番号
  （英語セット名は最長かつ定訳がなく、誰も検索しないため最初に落とす）
- 存在しない年・セット名は単に出力しない
- `authentic` / `rare` 等の根拠なき誇張語を検出して警告

**Condition Descriptor は一切ハードコードしていません。**
`27501` / `27502` / `275010`(PSA) / grade値ID を含め、
すべてキャッシュ済み `getItemConditionPolicies` から解決します。
テストでは**eBay が番号体系を変えた場合**を模擬し、
コードが追随することを固定しています。

解決不能なら**明示的に例外**を投げます。部分解決したまま送信すると、
不透明なエラーになるか、より悪い場合は**誤ったグレードが付いたまま成功**します。

**Certification Number は既定で送信しません。** eBay 上は任意項目であり、
実際に発送する個体と一致しない番号を送るのは誤記載になるためです。

**出品判定** (`eligibility.ts`) は要件の全条件を1箇所で検査し、
真偽値ではなく**具体的なブロッカーの一覧**を返します。
「対象外です」は運用者にとって無意味ですが、
「PSA判定が REVIEW / 悲観シナリオが ¥340 の赤字 / 実売データ不足」は
何を直せばよいかを伝えます。

`BLOCKING`（解消必須）と `REVIEW`（人が判断すれば通せる）を区別しています。

## 3. テストが見つけた実バグ 4件

いずれも本番で静かに損害を出す種類のものです。

### 3.1 カタカナ長音記号の破壊（重大）

`normalizeTitle` が **`ー`（U+30FC）をハイフンに変換**していました。
リザードン → リザ-ドン となり、**カタカナのカード名の大半で
名前マッチングが壊れます**。長音記号は句読点ではなく文字です。

### 3.2 `\bPSA\b` が "PSA10" にマッチしない（重大）

`A` と `1` の間に単語境界がないため、**データセット中で最も一般的な表記**である
「PSA10」で鑑定会社の検出が静かに失敗していました。
`\bPSA(?![A-Za-z])` に修正。

### 3.3 最低価格ソルバーの安全シナリオ降格（重大）

`MinPriceInput` が任意の `scenario` を再追加していたため、
`ProfitInput` をスプレッドすると**悲観シナリオの既定が静かに上書き**され、
円が動いた瞬間に赤字になる価格を、もっともらしい顔で返していました。

`scenarioOverride` に改名し、弱いシナリオの選択を明示的な行為にしました。
このケースを固定するテストを追加しています。

### 3.4 比較用正規化が空白を残していた

「リザードンex」と「リザードン ex」が 0.875 になり、同一カードが
別物と判定されうる状態でした。店舗ごとに空白の扱いが違うため、
比較時は完全除去が正しい挙動です。

さらに、eBay タイトルの脱落順が誤っており、検索語として価値のある
`GEM MINT` を、誰も検索しない長い英語セット名より先に捨てていました。
